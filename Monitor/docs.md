## 1. 项目定位（最重要的一节）

**这是一个「市场状态面板 + 归档器」，不是信号推送器。**

它的输出不是"买什么"，而是**"现在这个市场适不适合开启我那个均线策略"**——也就是 regime filter。

### 为什么是这个定位

Week 3 已经用数据证明了两件事：

1. 在 81 组均线参数里挑训练集最优的那组，Spearman ρ 接近 0——**挑参数就是在拟合噪音**
2. 1.7% 的来回成本能把毛收益直接吃成负数

所以下一步**不是继续调参数**，而是换一个正交的方向：判断什么时候**不要交易**。均线策略的钱主要亏在震荡市，能识别震荡市，比找到"更好的参数"价值大得多。

### 系统的三个价值，按重要性排序

| # | 价值 | 说明 |
|---|---|---|
| 1 | **归档** | 每个快照落盘、永不覆盖。三个月后你手上就有一份真正的样本外数据集——不是切一刀训练/测试那种伪样本外，是时间还没发生过的那种。**LSR 数据尤其如此：卖家不提供历史，今天不存就永远没有。** |
| 2 | **regime 判断** | 输出"当前是趋势/震荡/杠杆拥挤"的状态标签，用来决定策略开关 |
| 3 | **暴露真实数据的坑** | QC 云端的数据是干净对齐的。真实抓取会撞上时区、缺K线、上市日不同、代理丢包——这些回测里永远不会暴露 |

### 一句话判据（贯穿全程）

> **能拉到历史 = 能自己回测验证 = 可以用；拉不到历史 = 只能选择相信 = 只存不用。**

这条判据和数据源是谁、广告怎么写、花了多少钱都无关。

## 2. 红线清单（防跑偏）

以下事情在本项目**明确不做**。想做的时候回来看这一节。

| # | 不做什么 | 为什么 |
|---|---|---|
| 1 | ❌ 不做买卖信号推送 | 定位是状态面板。做成"金叉提醒"等于把 Week 3 的结论扔掉 |
| 2 | ❌ 不堆技术指标 | MACD/KDJ/RSI/CCI/WR 都是价格的平滑变换，互相高度相关。堆 10 个不是 10 份信息，只保证每天都有一个"说对了"的让你去挑 |
| 3 | ❌ 不把未验证的信号接进告警 | LSR「聪明钱」信号目前**无法回测**。Day 1 起只归档，Day 7 之前不允许接入任何判断逻辑 |
| 4 | ❌ 不做资金费率套利 | 实测榜首 VELO 显示 APR 4369%，但买边持仓量只有 $2996。这个榜按 APR 排序，最高的必然最不可交易。当反面教材记录即可 |
| 5 | ❌ 不做分钟级交易监控 | 限频 6 次/分钟。系统定位是日频 regime 判断，高频那条链路只负责归档 |
| 6 | ❌ 不优化参数 | 本项目一个参数都不"调优"。阈值先写死再跑，看完结果**不允许回头改阈值再看一遍**——那就是 Week 3 说的污染测试集 |
| 7 | ❌ 不加币种 | 就这 9 个。想加等第一版跑满一个月之后 |
| 8 | ❌ 不上数据库 | 9 币 × 3000 天，parquet 文件就够。别花时间搭 PostgreSQL |
| 9 | ❌ 不装 TA-Lib / ccxt | TA-Lib 要编译 C 库；ccxt 默认打不通的域名还得改 urls。指标自己写 5~10 行 pandas，符合本项目"理解底层"的理念 |
| 10 | ❌ 不下单、不碰交易 API Key | 本系统全程只读 |

## 3. 已确定的技术事实（实测，2026-08-17）

**不要再去试那些已经证明不通的路。**

### 3.1 网络

环境：WSL2 + 代理 `127.0.0.1:7890`（台湾节点）。**直连全部超时，代理是必需品。**

| 端点 | 状态 | 备注 |
|---|---|---|
| `api.binance.com` / `fapi.binance.com` | ❌ 完全超时 | DNS 被污染到 `74.86.151.162`，**放弃这条路** |
| `data-api.binance.vision` | ✅ 200 | 币安官方只读行情镜像，**无需 key** |
| `api.coinglass.site` | ✅ 200 | 中转站，手册认可域名 |
| `vip.coinglass.site` | ⚠️ 可用但非手册域名 | 只转发 Coinglass，无 LSR。**统一用 `api.coinglass.site`** |
| OKX / Bybit | ✅ 200 | 备份现货源 |
| CoinGecko | ⚠️ 时通时不通 | 不作为关键依赖 |

> **代理有丢包**：同一个请求时通时不通，实测多次。**任何请求都必须带重试**，这是硬性要求不是优化项。

### 3.2 数据源与限频

| 数据 | 地址 | 认证 | 限频 |
|---|---|---|---|
| 现货 OHLCV 日线 | `data-api.binance.vision/api/v3/klines` | 无 | 宽松 |
| funding / OI / 大户多空比 / 主动买卖量 | `api.coinglass.site/api/futures/*` | `X-API-Key` | **6 次/分钟** |
| LSR 聪明钱信号 | `api.coinglass.site/api/lsr/*` | `X-API-Key` | **6 次/分钟（独立桶）** |

两个桶**分开计数**（错误文案分别是"用户在 coinglass 的速率超限"和"用户在 lsr 的速率超限"），可以并行用。

**请求间隔垫到 11 秒，实测 100% 成功。**

### 3.3 各数据的历史深度（决定能不能回测）

| 数据 | 接口 | 深度 | 回测 |
|---|---|---|---|
| 现货 K 线 | binance.vision | BTC 2017-08 起 | ✅ |
| funding | `/api/futures/funding-rate/history` | 2332 条，2020-03-30 起 | ✅ |
| 持仓量 OI | `/api/futures/open-interest/history` | 2364 条，2020-02-27 起 | ✅ |
| 大户持仓多空比 | `/api/futures/top-long-short-position-ratio/history` | 2285 条，2020-05-16 起 | ✅ |
| 主动买卖量 | `/api/futures/taker-buy-sell-volume/history` | 2022 条，2019-09-08 起 | ✅ |
| **LSR 聪明钱信号** | `/api/lsr/v2/signals` | **仅当前快照，最长回看 4h** | ❌ **只能自己攒** |
| KOL 共识 | `/api/lsr/consensus/v1/*` | 未测（撞限频） | 待定，大概率同上 |

各币上市日不同，**SUI 最晚：2023-05-03**。任何跨币比较都要处理不等长历史。

### 3.4 已知的坑

| 坑 | 说明 |
|---|---|
| **funding 单位不统一** | Coinglass 返回**百分数**（`0.008579` = 0.0086%/8h），Gate.io 返回小数。**入库统一转成年化小数**，源头单位在抓取层消化 |
| **LSR 样本小且自选** | BTC 的 `ov_total_traders` 只有 **1607 人**，是主动公开晒单的人，非随机样本。叫"公开晒单者仓位"比"聪明钱"准确 |
| **大户多空比口径变过** | 币安历史上改过统计方式，回测要**分段看**，别一条曲线拉到底 |
| **`null` 不是 0** | 手册明确：某些字段无值时返回 `null`，不要当 0 处理 |
| **WSL2 的 cron 不自启** | 用 Windows 任务计划程序调 `wsl.exe -e <venv python> <script>` 更可靠 |
| **成本假设要重算** | Week 1 验证的是 QC/Coinbase 单边 0.85%。币安现货 taker 0.1%，差近一个数量级，会显著改变 Week 3 的结论 |

### 3.5 运行环境：归档跑在服务器上（2026-08-17 起）

归档器**不在本机跑**。本机是 WSL2，关机/重启就断，而这个归档器的全部价值在于连续性。

| 项 | 值 |
|---|---|
| 服务器 | `ubuntu@43.155.206.51`，Tencent Cloud **首尔（KR）**，Ubuntu 22.04 |
| 部署路径 | `/home/ubuntu/QuantLearn` |
| 运行方式 | systemd 服务 `lsr-archive`，`Restart=always`，开机自启已启用 |
| 代理 | **不需要**，两个数据源在服务器上直连均 200 |
| 本地数据 | 用 `deploy/pull_data.sh` 按需拉回，服务器是唯一数据权威 |

```bash
# 部署 / 更新（幂等）
Monitor/deploy/deploy.sh -y ubuntu@43.155.206.51

# 看状态
ssh ubuntu@43.155.206.51 'systemctl status lsr-archive --no-pager'
ssh ubuntu@43.155.206.51 'tail -5 ~/QuantLearn/Monitor/data/archive.log'

# 拉数据回本地（合并去重，不覆盖）
Monitor/deploy/pull_data.sh ubuntu@43.155.206.51:/home/ubuntu/QuantLearn
```

**纪律：限频 6 次/分钟是按 key 计的，只能在一个地方跑归档。** 服务器跑起来之后，
本地不要再执行 `archive_lsr.py`，否则两边互相挤兑配额、互相打 429。

已实测：`kill -9` 主进程后 systemd 在 30s 内拉起（`NRestarts=1`），服务恢复 running。

### Day 7 · 回测验证：把"相信"变成"验证" ⭐ 关键的一天

**这一天是整个项目的分水岭。** 前 6 天在建管道，这天开始用第 3 周学的方法**检验数据到底有没有用**。

**产出** `research/`，复用 Week_3 `code.py` 的向量化框架：

1. **funding 因子检验**：funding 年化进入历史前/后 10% 分位后，未来 5/10/20 天收益如何？**正着做和反着做各测一遍**
2. **大户多空比检验**：同上。重点看它是顺向还是反向指标——**别预设答案**
3. **ER 作为 regime filter**：Week 3 那个 20/60 策略，加上"仅在 ER > 阈值时开仓"，测试区间表现变化多少
4. **成本重算**：`COST` 从 0.85% 改成币安的 0.1%，Week 3 的结论翻不翻面

**验收**
- [ ] 每个因子都有训练/测试拆分，**测试集只看一次**
- [ ] 明确写下结论：**哪个因子有效、哪个无效**。"无效"是完全合格的结论，写下来比硬找出效果更有价值

**Day 1 偏离记录**

1. **归档字段存 32 个而非 12~15**。成本不对称：多存一个字段约 +5KB/天（32 字段 ×
   9 币 × 288 次/天 ≈ 150KB/天、50MB/年）；漏存一个则三个月后永远补不回来。
   砍掉的 43 个是 `*_pct` 字符串和 `*_abs`，都能从保留字段算出来。
2. **`config.py` 增加 `.env` 自动加载**（仓库根 + `Monitor/` 两处都扫）。起因是
   `Monitor/` 下有个 0 字节的空 `.env`，会让人误以为 key 填那儿就能生效。
   代理配置也一并收进 `.env`——实测本机 profile **不设**代理，定时任务调起来
   环境是干净的，不在代码里注入就会静默失败。
3. **归档改为部署到服务器**（原计划 Day 6 才做定时）。提前的理由同 Day 1 本身：
   数据不可追溯，本机 WSL2 关机就断。见 3.5 节。

**Day 1 踩到的坑**
- Ubuntu 上 `import venv` 能过但缺 `ensurepip`，到建 venv 那步才报错。
  探测要查 `ensurepip` 不是 `venv`（已修进 `deploy.sh`）。
- `pull_data.sh` 最初用 `rsync --update`，**会丢数据**：同一天本地和服务器
  各自产生过快照，服务器文件 mtime 更新就会把本地 126 行覆盖成 18 行。
  已改成落暂存区 + 按 `(fetched_at, symbol)` 合并去重。
  **教训：两端各自写同名文件时，同步语义必须是合并不是覆盖。**

**Day 1 实测补充**
- 14 个快照里有 13 个不同的 `source_updated_at` → 存在**源数据未更新**的快照，
  说明源不是严格 2 分钟一变，分析时要按 `source_updated_at` 去重而不是按 `fetched_at`。
- 一小时内 BTC `ratio` 在 0.294~0.329 之间移动，数据是活的。
- 首个快照即观察到：BTC 多头平均成本 66421 / 空头 64479，当时价约 63500
  → **多头整体套牢、空头浮盈**。这类内部一致性可作为数据可信度的持续校验。
