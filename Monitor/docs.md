## 1. 项目定位（最重要的一节）

**这是一个「市场状态面板 + 归档器」，不是信号推送器。**

它的输出不是"买什么"，而是**"现在这个市场适不适合开启我那个均线策略"**——也就是 regime filter。

### 为什么是这个定位

Week 3 已经用数据证明了两件事：

1. 在 81 组均线参数里挑训练集最优的那组，Spearman ρ 接近 0——**挑参数就是在拟合噪音**
2. 1.7% 的来回成本能把毛收益直接吃成负数

所以下一步**不是继续调参数**，而是换一个正交的方向：判断什么时候**不要交易**。均线策略的钱主要亏在震荡市，能识别震荡市，比找到"更好的参数"价值大得多。

### 系统的三个价值，按重要性排序

| # | 价值 | 说明 |
|---|---|---|
| 1 | **归档** | 每个快照落盘、永不覆盖。三个月后你手上就有一份真正的样本外数据集——不是切一刀训练/测试那种伪样本外，是时间还没发生过的那种。**LSR 数据尤其如此：卖家不提供历史，今天不存就永远没有。** |
| 2 | **regime 判断** | 输出"当前是趋势/震荡/杠杆拥挤"的状态标签，用来决定策略开关 |
| 3 | **暴露真实数据的坑** | QC 云端的数据是干净对齐的。真实抓取会撞上时区、缺K线、上市日不同、代理丢包——这些回测里永远不会暴露 |

### 一句话判据（贯穿全程）

> **能拉到历史 = 能自己回测验证 = 可以用；拉不到历史 = 只能选择相信 = 只存不用。**

这条判据和数据源是谁、广告怎么写、花了多少钱都无关。

## 2. 红线清单（防跑偏）

以下事情在本项目**明确不做**。想做的时候回来看这一节。

| # | 不做什么 | 为什么 |
|---|---|---|
| 1 | ❌ 不做买卖信号推送 | 定位是状态面板。做成"金叉提醒"等于把 Week 3 的结论扔掉 |
| 2 | ❌ 不堆技术指标 | MACD/KDJ/RSI/CCI/WR 都是价格的平滑变换，互相高度相关。堆 10 个不是 10 份信息，只保证每天都有一个"说对了"的让你去挑 |
| 3 | ❌ 不把未验证的信号接进告警 | LSR「聪明钱」信号目前**无法回测**。Day 1 起只归档，Day 7 之前不允许接入任何判断逻辑 |
| 4 | ❌ 不做资金费率套利 | 实测榜首 VELO 显示 APR 4369%，但买边持仓量只有 $2996。这个榜按 APR 排序，最高的必然最不可交易。当反面教材记录即可 |
| 5 | ❌ 不做分钟级交易监控 | 限频 6 次/分钟。系统定位是日频 regime 判断，高频那条链路只负责归档 |
| 6 | ❌ 不优化参数 | 本项目一个参数都不"调优"。阈值先写死再跑，看完结果**不允许回头改阈值再看一遍**——那就是 Week 3 说的污染测试集 |
| 7 | ❌ 不加币种 | 就这 9 个。想加等第一版跑满一个月之后 |
| 8 | ❌ 不上数据库 | 9 币 × 3000 天，parquet 文件就够。别花时间搭 PostgreSQL |
| 9 | ❌ 不装 TA-Lib / ccxt | TA-Lib 要编译 C 库；ccxt 默认打不通的域名还得改 urls。指标自己写 5~10 行 pandas，符合本项目"理解底层"的理念 |
| 10 | ❌ 不下单、不碰交易 API Key | 本系统全程只读 |

## 3. 已确定的技术事实（实测，2026-08-17）

**不要再去试那些已经证明不通的路。**

### 3.1 网络

环境：WSL2 + 代理 `127.0.0.1:7890`（台湾节点）。**直连全部超时，代理是必需品。**

| 端点 | 状态 | 备注 |
|---|---|---|
| `api.binance.com` / `fapi.binance.com` | ❌ 完全超时 | DNS 被污染到 `74.86.151.162`，**放弃这条路** |
| `data-api.binance.vision` | ✅ 200 | 币安官方只读行情镜像，**无需 key** |
| `api.coinglass.site` | ✅ 200 | 中转站，手册认可域名 |
| `vip.coinglass.site` | ⚠️ 可用但非手册域名 | 只转发 Coinglass，无 LSR。**统一用 `api.coinglass.site`** |
| OKX / Bybit | ✅ 200 | 备份现货源 |
| CoinGecko | ⚠️ 时通时不通 | 不作为关键依赖 |

> **代理有丢包**：同一个请求时通时不通，实测多次。**任何请求都必须带重试**，这是硬性要求不是优化项。

### 3.2 数据源与限频

| 数据 | 地址 | 认证 | 限频 |
|---|---|---|---|
| 现货 OHLCV 日线 | `data-api.binance.vision/api/v3/klines` | 无 | 宽松 |
| funding / OI / 大户多空比 / 主动买卖量 | `api.coinglass.site/api/futures/*` | `X-API-Key` | **6 次/分钟** |
| LSR 聪明钱信号 | `api.coinglass.site/api/lsr/*` | `X-API-Key` | **6 次/分钟（独立桶）** |

两个桶**分开计数**（错误文案分别是"用户在 coinglass 的速率超限"和"用户在 lsr 的速率超限"），可以并行用。

**请求间隔垫到 11 秒，实测 100% 成功。**

### 3.3 各数据的历史深度（决定能不能回测）

| 数据 | 接口 | 深度 | 回测 |
|---|---|---|---|
| 现货 K 线 | binance.vision | BTC 2017-08 起 | ✅ |
| funding | `/api/futures/funding-rate/history` | 2332 条，2020-03-30 起 | ✅ |
| 持仓量 OI | `/api/futures/open-interest/history` | 2364 条，2020-02-27 起 | ✅ |
| 大户持仓多空比 | `/api/futures/top-long-short-position-ratio/history` | 2285 条，2020-05-16 起 | ✅ |
| 主动买卖量 | `/api/futures/taker-buy-sell-volume/history` | 2022 条，2019-09-08 起 | ✅ |
| **LSR 聪明钱信号** | `/api/lsr/v2/signals` | **仅当前快照，最长回看 4h** | ❌ **只能自己攒** |
| KOL 共识 | `/api/lsr/consensus/v1/*` | 未测（撞限频） | 待定，大概率同上 |

各币上市日不同，**SUI 最晚：2023-05-03**。任何跨币比较都要处理不等长历史。

### 3.4 已知的坑

| 坑 | 说明 |
|---|---|
| **funding 单位不统一** | Coinglass 返回**百分数**（`0.008579` = 0.0086%/8h），Gate.io 返回小数。**入库统一转成年化小数**，源头单位在抓取层消化 |
| **LSR 样本小且自选** | BTC 的 `ov_total_traders` 只有 **1607 人**，是主动公开晒单的人，非随机样本。叫"公开晒单者仓位"比"聪明钱"准确 |
| **大户多空比口径变过** | 币安历史上改过统计方式，回测要**分段看**，别一条曲线拉到底 |
| **`null` 不是 0** | 手册明确：某些字段无值时返回 `null`，不要当 0 处理 |
| **WSL2 的 cron 不自启** | 用 Windows 任务计划程序调 `wsl.exe -e <venv python> <script>` 更可靠 |
| **成本假设要重算** | Week 1 验证的是 QC/Coinbase 单边 0.85%。币安现货 taker 0.1%，差近一个数量级，会显著改变 Week 3 的结论 |

### 3.5 运行环境：归档跑在服务器上（2026-08-17 起）

归档器**不在本机跑**。本机是 WSL2，关机/重启就断，而这个归档器的全部价值在于连续性。

| 项 | 值 |
|---|---|
| 服务器 | `ubuntu@43.155.206.51`，Tencent Cloud **首尔（KR）**，Ubuntu 22.04 |
| 部署路径 | `/home/ubuntu/QuantLearn` |
| 运行方式 | systemd 服务 `lsr-archive`，`Restart=always`，开机自启已启用 |
| 代理 | **不需要**，两个数据源在服务器上直连均 200 |
| 本地数据 | 用 `deploy/pull_data.sh` 按需拉回，服务器是唯一数据权威 |

```bash
# 部署 / 更新（幂等）
Monitor/deploy/deploy.sh -y ubuntu@43.155.206.51

# 看状态
ssh ubuntu@43.155.206.51 'systemctl status lsr-archive --no-pager'
ssh ubuntu@43.155.206.51 'tail -5 ~/QuantLearn/Monitor/data/archive.log'

# 拉数据回本地（合并去重，不覆盖）
Monitor/deploy/pull_data.sh ubuntu@43.155.206.51:/home/ubuntu/QuantLearn
```

**纪律：限频 6 次/分钟是按 key 计的，只能在一个地方跑归档。** 服务器跑起来之后，
本地不要再执行 `archive_lsr.py`，否则两边互相挤兑配额、互相打 429。

已实测：`kill -9` 主进程后 systemd 在 30s 内拉起（`NRestarts=1`），服务恢复 running。

### Day 7 · 回测验证：把"相信"变成"验证" ⭐ 关键的一天

**这一天是整个项目的分水岭。** 前 6 天在建管道，这天开始用第 3 周学的方法**检验数据到底有没有用**。

**产出** `research/`，复用 Week_3 `code.py` 的向量化框架：

1. **funding 因子检验**：funding 年化进入历史前/后 10% 分位后，未来 5/10/20 天收益如何？**正着做和反着做各测一遍**
2. **大户多空比检验**：同上。重点看它是顺向还是反向指标——**别预设答案**
3. **ER 作为 regime filter**：Week 3 那个 20/60 策略，加上"仅在 ER > 阈值时开仓"，测试区间表现变化多少
4. **成本重算**：`COST` 从 0.85% 改成币安的 0.1%，Week 3 的结论翻不翻面

**验收**
- [ ] 每个因子都有训练/测试拆分，**测试集只看一次**
- [ ] 明确写下结论：**哪个因子有效、哪个无效**。"无效"是完全合格的结论，写下来比硬找出效果更有价值

### 6.2c funding 的两个口径（Day 3 发现，会直接影响 Day 7）

**问题**：Coinglass 的 1d K 线是**当天 3 次结算的 OHLC 聚合**。最初用 `close`
（日末最后一次结算）代表全天，这个口径会出系统性偏差：

| 币 | close 口径 | mid 口径 | 差 |
|---|---|---|---|
| XRP | +9.14% | −1.22% | **符号相反** |
| SOL | +4.16% | −1.06% | **符号相反** |
| BNB | 0.00% | +3.71% | close 判成"零成本" |

对 funding 因子而言**符号就是全部信号**，这个偏差留到 Day 7 会直接得出错误结论。

**现在的处理**：存两列，原始 OHLC 一列不删。

| 列 | 算法 | 适用 |
|---|---|---|
| `funding_annualized` | `close × 3 × 365 / 100` | 日末瞬时水平 |
| `funding_annualized_mid` | `(high+low)/2 × 3 × 365 / 100` | 当天中枢水平，抗日末归零噪音 |

**Day 7 必须两个口径都跑。结论不一致 = 这个因子对口径敏感，本身就是重要发现。**

要精确的"当日实际支付总额"得拉 8h 明细逐笔求和（需分页，约 27 次额外请求），
留到确认 funding 因子有效之后再做。

**BNB / LINK 的零值是真实的，不是脏数据。** 8h 明细确认整个周期就是 `0.000000`。
机制：币安 `funding = premium + clamp(interest − premium, ±0.05%)`，对利率设为 0
的交易对，溢价在 ±0.05% 带内时两项正好抵消 → funding 恰好为 0。
零值占比：BNB 49.2%、LINK 3.7%、其余 0%。**做统计时不能把这些当缺失值丢掉。**

### 6.3b 面板与定时（Day 6）

#### 产出

| 文件 | 作用 |
|---|---|
| `panel.py` | 拼第 1~3 层 + Coinglass 四件套 → 快照 + markdown 报告 |
| `run_daily.sh` | 日频流水线：取数 → 质检 → 指标 → 横截面 → 面板 |
| `deploy/panel-daily.service` | oneshot 单元 |
| `deploy/panel-daily.timer` | 每天 **00:30 UTC** 触发 |

#### 三个设计决定

**1. 面板日期锚定"现货最后一根已收盘 K 线"。**
Coinglass 那几个指标当天就有值，但那是没走完的一天。混进来快照就不可复现——
同一天上午和晚上跑会得到不同的数字。所以面板永远是「昨天」。

**2. timer 定在 00:30 UTC，且必须显式写 `UTC`。**
币安日线 00:00 UTC 收盘，留 30 分钟给交易所出数据和镜像同步。
服务器时区是 CST，`OnCalendar` 不写 UTC 会差 8 小时。
实测排程显示 `08:30:58 CST` = `00:30 UTC`，✔ 解释正确。
`Persistent=true`：关机错过触发点，开机补跑——少一天就永远少一天。

**3. oneshot 不加 `Restart=`。**
和常驻的 `lsr-archive` 相反。失败就等下一次 timer，**不要自动重试**：
重试会撞上 Coinglass 6 次/分钟的限频，越重试越堵。

流水线内部区分致命/非致命：取数和计算失败直接中止（**拿旧数据算出来的面板
看起来是新的，比没有更危险**），Coinglass 那步允许降级（它自己会沿用已存历史，
前 3 层不依赖它）。

#### 快照纪律

`data/snapshots/YYYY-MM-DD.{parquet,md}`，**一天一个，默认跳过已存在的日期**，
只有 `--force` 才覆盖。实测：重跑同一天 → 跳过；`--force` → 覆盖；换日期 → 新建。

这份归档三个月后才显出价值，现在每次静默覆盖都是在毁掉未来的样本。

#### 验收结果

| 验收项 | 结果 |
|---|---|
| 手动跑一次，快照文件生成 | ✅ `2026-08-16/17` 的 parquet + md |
| **定时任务真的自动跑过** | ✅ 用临时 drop-in 让 timer 60s 后触发，`10:24:35 CST` 准点起，`TriggeredBy: panel-daily.timer`，7 分钟后 `Result=success` |
| 重复跑同一天不重复不覆盖 | ✅ 重跑跳过、`--force` 覆盖、换日期新建 |

真实排程验证：`NEXT = Wed 2026-08-19 08:32:35 CST`，服务器时区 CST(UTC+8)
换算回 **00:32 UTC**（00:30 + 最多 5 分钟随机延迟），UTC 解释正确。

顺带确认了重试机制在真实条件下有效：流水线日志里出现两次上游 429
（`Coinglass 上游 Key 当前窗口额度不足`），退避后都成功，没有中断流水线。

#### 踩到的两个坑

**坑 1：服务跑成了 root**

两个 unit 都没写 `User=`，systemd 默认以 root 跑，产出的数据文件属主是 root：

```
-rw-r--r-- 1 root   root   2026-08-17.parquet   ← 服务写的
-rw-rw-r-- 1 ubuntu ubuntu 2026-08-18.parquet   ← 手动跑的
```

后果：**ubuntu 用户手动跑脚本会写不动历史文件**，而且属主混乱难查。
这类问题不会立刻报错，等到某天手动补数据才炸。

修法：两个 unit 加 `User=%USER%` / `Group=%USER%`，`deploy.sh` 从
`id -un` 探测远程用户后替换，并 `chown -R` 收回历史文件。
另外 `enable --now` **不会重启已在运行的服务**，改了 unit 必须显式 `restart` 才生效，
`deploy.sh` 里补上了。修完实测：两个服务身份都是 `ubuntu`，root 属主残留 0 个。

**坑 2：日志每行写了两遍**

`run_daily.sh` 的 `log()` 用 `tee -a "$LOG"`，而 unit 里 `StandardOutput=append:` 
又把 stdout 接到同一个文件 —— 同一行进了两次。
子进程输出只有一份（它们是 `>>"$LOG"` 直接写的），正好定位到是 `tee` 的问题。

修法：用 systemd 注入的 `INVOCATION_ID` 判断运行环境 —— 有它就只 `echo`
（systemd 负责落盘），没有就 `tee`（手动跑时终端和文件都要有）。
实测重复行数从 20 降到 **0**。

### 6.4 因子验证结果（Day 7）⭐

拆分点 `2024-01-01`。训练 2020-03→2023-12，测试 2024-01→2026-08。**测试集只看了一次。**

#### 总表

| 因子 | 训练区间 | 测试区间 | 方向 | **结论** |
|---|---|---|---|---|
| funding（close 口径） | 20d 超额 +10.8%，t=**0.81** | 超额 +3.2%，t=**0.30** | 顺向 | ❌ **无效** |
| funding（mid 口径） | 20d 超额 +13.0%，t=**0.65** | 超额 +2.9%，t=**0.28** | 顺向 | ❌ **无效** |
| 大户多空比 | 20d 超额 −5.9%，t=**−0.75** | 超额 +0.2%，t=**0.01** | 训练反向，测试消失 | ❌ **无效** |
| ER regime filter | — | Sharpe 改善 **5/9** | 掷硬币 | ❌ **不改善风险调整收益** |

**四个因子，零个有效。** 这是完全合格的结论——docs.md 第 5 节写过：
「"无效"是完全合格的结论，写下来比硬找出效果更有价值」。

#### funding：超额看着很大，t 值撑不住

训练集上 funding 高分位后 20 日平均涨 17.2%，基准只有 6.5%，超额 +10.8pp。
看起来很诱人。但 t 只有 0.81，因为：

- 极端 funding 集中在少数几波行情里 → 独立时间簇只有 **7 个**
- 折算有效自由度后 n_eff ≈ 7 × 1.38 ≈ 10
- crypto 的 20 日收益标准差极大

到测试集，+10.8pp 缩水成 +3.2pp。**训练集那个"超额"就是噪音。**

还有一层混淆没排除：高 funding 本来就发生在牛市里，牛市的前瞻收益自然高。
所以这更像是 regime 重叠，不是 funding 的预测力。

#### 大户多空比：符号一致但幅度不显著，且测试集消失

训练集分年看，高分位后的超额收益 **2021/2022/2023 三年都是负的**
（−13.1 / −4.0 / −2.3pp），符号一致，方向符合"拥挤即反向"的理论。
但每年的 |t| 都 < 1.7，且到测试集（2024/2025/2026）超额变成 −0.4 / −2.9 / −5.5pp
而汇总后是 **+0.2pp，t=0.01** ——完全消失。

三年符号一致在零假设下的概率约 25%，本来就算不上证据。

#### ER regime filter：降的是暴露，不是风险

这是最需要小心的一个，因为**表面数字很好看**：

| 维度 | 结果 | 中位改善 |
|---|---|---|
| 年化 | 5/9 改善 | +9.6pp |
| **最大回撤** | **8/9 改善** | **+20.1pp** |
| **Sharpe** | **5/9 改善** | +0.34 |

回撤 8/9 改善看着很强，但**机制不对**：ER 过滤把持仓占比从 ~55% 压到 ~15%。
在市场里待的时间少了 2/3，回撤当然小——**这是降暴露，不是择时**。
同样的效果，直接把仓位缩到 15% 就能拿到，不需要任何指标。

**收益随仓位线性缩放，Sharpe 不变，所以 Sharpe 才是暴露中性的比较。**
Sharpe 只有 5/9 改善 = 掷硬币。**ER 过滤没有提供择时能力。**

另一个反直觉的发现：**ER 过滤让交易笔数涨了 2.5 倍**（91 → 250）。
因为 ER 在 0.30 附近反复穿越，仓位跟着反复开关。过滤器本身是"抖"的。
这让它对成本极度敏感——BTC 测试区间，QC 0.85% 成本下成本拖累从 18.7% 飙到
**49.3%**，把 +3.03% 直接打成 −1.65%。

> 注：`ER_MIN=0.30` 是跑之前写死的，看完结果**没有回头调**。
> 调了再看一遍，测试集就变成第二个训练集了。

#### 成本重算：Week 3 的结论对成本假设有多敏感

| | QC/Coinbase 0.85% | 币安 0.10% |
|---|---|---|
| 成本拖累中位数 | **18.3%** | **2.1%** |
| 由负转正的组合 | — | **1/18**（LINK 测试区间 −12.4% → +3.4%） |

成本降 8.5 倍，拖累降到 1/9，但**只有 1/18 的组合由负转正**。

结论：Week 3「手续费吞噬收益」的结论**在币安成本下大幅减弱，但策略并没有因此
变得有效**——亏钱的还是亏钱。成本不是双均线策略的主要问题，**方向判断才是**。

这条修正了立项时的一个假设：我原以为换成币安成本会显著改变 Week 3 的结论，
实测只改变了程度，没有改变性质。

#### ⭐ 方法论上最重要的一条：9 个币不是 9 次独立试验

Day 5 实测 N_eff = 1.38。把「5/9」「8/9」当成 9 次独立试验是错的：

```
年化改善 5/9 → 折算后约 1/1 次独立观察，单侧 p ≈ 0.50
回撤改善 8/9 → 折算后约 1/1 次独立观察，单侧 p ≈ 0.50
```

**在这个标的池里，任何"9 个币里有 N 个成立"的说法都撑不起结论。**
本项目所有 t 值都按「独立时间簇数 × N_eff」折算，而不是按原始样本数——
后者会把显著性高估约 6.5 倍。

#### 对 Day 8 的直接后果

**没有任何因子通过验证，所以 Day 8 的 regime filter 没有可接入的东西。**

docs.md 红线第 3 条写的是「只允许接入 Day 7 验证通过的因子」。现在通过的是空集。
Day 8 应该如实反映这一点，而不是硬凑一个状态标签出来。
